# KAPE DOZ software acceptance matrix

Date: 7 November 2026, Asia/Manila. Scope: [EXECUTION PLAN.md](<EXECUTION PLAN.md>). Current results: [VERIFICATION STATUS.md](<VERIFICATION STATUS.md>). Source manifest: [RELEASE CANDIDATE SOURCE HASHES.json](<RELEASE CANDIDATE SOURCE HASHES.json>).

There are 45 acceptance cases, with five per workflow family and five cross-role journeys. A case passes when all its assertions have current evidence. Partial status records verified behavior alongside the outstanding assertions.

## Evidence rules

- Record the case ID, test/runner path, command, environment and source revision or SHA-256 manifest.
- Record the observed result, expected ledger changes and relevant immutable command/order IDs using synthetic data.
- Record logs, report paths and screenshots as appropriate; store temporary diagnostics under ignored `scratch/`.
- Use Passed, Failed, Not run, Not implemented or Blocked. A blocked row identifies the exact missing dependency or decision.
- Invalidate a prior pass after changes to its affected source, contracts, fixtures or configuration; rerun before candidate acceptance.

Physical-device checks use a separate status, **Device validation pending**, until real equipment is exercised. Mocked hardware/provider responses must be labeled. Manually recorded external payments or refunds must never be presented as app-executed provider charges or transfers.

Receipt/invoice classification, actual tax/pricing rules, and applicable statutory discount policies (`D02`) require client confirmation before live commercial checkout. Software acceptance cases use explicitly named synthetic fixtures and versioned branch configuration (`branch_config`).
